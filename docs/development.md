# Development

`xcli` is an experimental, read-only Phase 1 Rust package and binary. Use Rust
edition 2024 with MSRV **1.88**. macOS Chrome is the initial credential target;
Ubuntu exercises portable code and unsupported-platform behavior, not Linux
browser authentication. No Windows support or Linux release artifact is promised.

## Contributor checks

Install stable Rust with rustfmt and Clippy, plus Rust 1.88.0 for compatibility
checks. macOS builds need Apple's command-line developer tools and SDK; Linux
builds need a C toolchain for native dependencies. Commit `Cargo.lock`; dependency
updates must remain compatible with the MSRV and locked builds.

Run the same ordered checks as `.github/workflows/ci.yml`:

```sh
export RUSTFLAGS="-D warnings"
export CARGO_INCREMENTAL=0
cargo fmt --all --check
cargo clippy --all-targets --all-features -- -D warnings
cargo build --locked
cargo test --locked
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps
cargo +1.88.0 build --locked
cargo +1.88.0 test --locked
```

CI runs the stable sequence and separate MSRV build/test jobs on Ubuntu and
macOS. Keep the order intact. Where installed, validate workflow edits with:

```sh
actionlint .github/workflows/ci.yml .github/workflows/release.yml
```

## Dependency rationale

Keep dependencies narrowly scoped; document new features, native requirements,
license/provenance, and MSRV consequences when adding or updating them.
`Cargo.toml` and `Cargo.lock` are authoritative for the actual versions/features.

| Dependency | Purpose |
| --- | --- |
| `clap` with derive | Typed CLI parsing, help, and argument validation. |
| `serde`, `serde_json` | Typed configuration, normalized JSON output, and protocol fixtures. |
| `reqwest` with blocking/JSON/rustls and default features disabled | Synchronous HTTP for the CLI with TLS, without requiring a separate application async runtime or system OpenSSL setup. |
| `url` | Structural URL parsing and safe request construction instead of string matching. |
| `httpdate` | Correct handling of HTTP-date as well as numeric Retry-After headers. |
| `sha2` | SHA-256 cache keys and Chromium cookie host-digest validation; not password storage. |
| `tempfile` (dev-only) | Isolated synthetic test directories; not used for browser credential exports. |
| `libc` | Native descriptor-relative secure file operations and advisory locks; avoids handwritten platform ABI constants. |
| `zeroize` | Best-effort cleanup of owned credential/key buffers; does not guarantee erasure of every copy or OS buffer. |

The native credential implementation uses the following pieces; their inclusion is **not** evidence of verified live authentication:

| Credential component | Purpose and boundary |
| --- | --- |
| Native `Security.framework` | In-process macOS Keychain access through OS-supported APIs, respecting consent and access denial. No shell command that prints a secret, key creation/reset, or protection bypass. |
| `rusqlite` | Read-only Chrome cookie database access with a consistent SQLite snapshot/transaction that respects WAL state. Bundled SQLite, if enabled, needs a C compiler and avoids reliance on host SQLite versions. |
| `aes`, `cbc` | Chromium-compatible AES-128-CBC decoding with strict padding validation for the explicitly supported format; not a new encryption design. |
| `pbkdf2`, `sha1` | Compatibility with Chromium's existing PBKDF2-HMAC-SHA1 key derivation. SHA-1 and legacy iteration counts are for format compatibility only, never recommendations for new password storage. |

Keep platform-specific Keychain code behind macOS compilation guards. Unknown
schemas/encryption, unavailable keys, or denied access must fail closed. Never
add a fallback that changes permissions, bypasses OS protections, or tries a
different profile/account silently.

## Safe tests and protocol changes

Normal tests must be offline and deterministic: inject HTTP responses and
credential providers; use temporary synthetic profiles, databases, account IDs,
and cookie values. Do not read a developer's browser profile or Keychain, launch
or control a browser, or make live authenticated requests from CI/tests.

Cover URL/ID validation, provider routing, unavailable/malformed upstream data,
HTTP errors and rate limits, stable-identity mismatch, account/cache isolation,
bounded/repeated cursors, partial results, credential redaction, and unsupported
storage. Credential fixtures should cover digest/padding failures, domain and
session ambiguity, unknown encryption, SQLite consistency, and denied consent.
Prefer injected state over modifying process-global environment in tests.

Never commit cookies, authorization headers, Safe Storage keys, real profile
databases, private account responses, or secrets in logs, snapshots, issues,
artifacts, or model/tool transcripts. Redact fixtures before sharing. Zeroizing
buffers does not make logging them safe. FxTwitter must never receive X session
material; authenticated requests must not fall back to public or other-account
access. A read-only CLI still handles account-level credentials.

Keep GraphQL definitions/parsers isolated and review only explicitly verified
read queries. See [protocol research](protocol-research.md) for provenance and
remaining blockers. Bird is a protocol/design reference, **not a dependency**;
no Bird implementation code is vendored. Do not copy unreviewed historical
operation IDs or code. Any future code reuse requires an independent provenance
and license review with required notices.

Source inspection and synthetic tests do not establish live authenticated
interoperability or real Chrome compatibility. Any live verification needs
separate explicit user consent and a user-controlled account, with sanitized
results only. Stop on unsupported protections, identity uncertainty, or rate
limits rather than attempting a workaround.

Phase 1 has no X mutations. Phase 2 is tracked in
[#1](https://github.com/codesoda/x-cli/issues/1) and [phase-2.md](phase-2.md);
posting, DMs, account rotation, and proxy rotation remain out of scope.

## Changelog and releases

Follow the `discuss-cli` Keep a Changelog/action conventions: maintain
`CHANGELOG.md` with `## [Unreleased]` and grouped notable changes. Do not invent
release history or imply experimental auth has been live-verified.

When maintainers explicitly authorize a release, the intended tagged commit
must contain a nonempty `## [X.Y.Z]` or `## [vX.Y.Z]` section (normally dated),
and `Cargo.toml`'s package version must equal the tag without its leading `v`.
Keep the lockfile aligned. An Unreleased-only changelog deliberately blocks
release publication until versioned notes exist.

`.github/workflows/release.yml` runs on `v*` tag pushes or manual dispatch with
an **existing** `v`-prefixed version tag. It validates the input before checking
out `refs/tags/<tag>`; a branch name or absent tag cannot substitute the default
branch. It resolves that tag to a commit, validates package version and notes,
and invokes the full reusable CI workflow against that exact commit. Only then
do native Apple silicon (`macos-15`) and Intel (`macos-15-intel`) jobs perform
locked release builds and tests. Publishing also rechecks that the tag has not
moved from the tested commit.

Assets contain the `xcli` executable at the tarball root:

- `xcli-<tag>-aarch64-apple-darwin.tar.gz`
- `xcli-<tag>-x86_64-apple-darwin.tar.gz`
- `checksums-sha256.txt`

Only the publish job receives `contents: write`; the workflows default to read
permission and checkout does not persist credentials. Release notes come from
the validated tagged changelog, not generated history. Static workflow checks
are not a GitHub-hosted execution test. Adding these files does not itself
create a tag, publish to crates.io, or create a GitHub release; do not trigger
publication as a development smoke test.
